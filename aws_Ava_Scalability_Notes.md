## Sticky Sessions 
So what this is making sure each request a user makes, goes to the same server behind the load balancer. 

So the load balancer makes sure each EC2 instance has an equal amount of users, but Sticky Session "binds" a user to an instance. Instead of spreading all the requests across all instances.

This is handled via a cookie, to ensure the stickiness. This helps not loosing session data. 

It could imbalance the load across the EC2 instances though. 

Application Based Cookie
    Theres Custom Cookies:
        - Generated by the target
        - Custom Attributes required by the app
        - Cookie name must be specified for each target group
        - Can't use revered names AWSALB, AWSALBAPP, AWSALBTG
    Theres App Cookies:
        - Generated by the load balancer
        - Cooke name is always AWSALBAPP
Theres also Duration-based Cookies:
    - Generated by the load balancer
    - Cookie name is AWSALB for ALB, and AWSELB for CLB (Remember the classic load balancer is going away eventually)

You enable this by editing the target group: 
Target selection configuration. 
1 second - 7 days life time

## Cross Zone Load Balancer
So **with** Cross Zone load balancing, the load balancer looks at the how of the total traffic to hand to each zone. 

Zone A 50%
Zone B 50%

Then, the load balancer looks at the total amount of EC2 instances. So if theres ten, each EC2 will get about 10 percent of the total load. 

**Without** CRoss Zone Load Balancing:

Zone A 50%
Zone B 50% 

But lets say zone A has 2, and zone b has 8 EC2 instances
Then  what happens is half the traffic goes to zone A, and then each of those EC2s get 25% of the total traffic. 

The other 50% of the load goes to zone B, and devided up between those 8 host which is 6.25%. 

By default application load balancers will have cross zone enabled. It doesn't charge anything for inter AZ data. 

Network Load Balancers and Gateway Load Balancers
This is disable by default, if you enable it, it'll cost money. 

Classic is disabled by default, but no cost for it if it's enabled. 

## SSL TLS Certificates
The interesting this with this is a user will send data to your load balancer using certs to encrypt the data. Then the load balancer doess SSL termination and then send your now unencrypted data over the VPC to the EC2 Instance. 

SNI - Server Name Indication
Essentially this solved shared hosting so a load balancer knows which cert to use for which client. 

Client goes I wan't ianscooldomain.cool, the ALB says yep I have that let me grab the cert, then it send the traffic onto the correct target group(s).

This only works for ALB and NLB, also CloudFront

App and Network load balancers support multiple listenrrs with multiple SSL certs, uses SNI to make this work.

## Connection Draining, Deregistration Delay (ALB NLB)
Time to complete encryption in motion while that specific EC2 instance is de-registering or in an unhealthy state.

The ELB knows to stop sending requests to that EC2, but will wait for current connection to finish. 

You can set this value between 1 - 3600 seconds, or set it to 0 to disable this feature. 
Set as a low value if you know your requests are short and fast otherwise your just wasting time. 

## Autoscaling Group
Quick and dirty, this either adds EC2 instance is the load is heavy, or removes EC2 instances if the load is low 
Can add min or max parameters to ensure you always have enough but not so many that costs spin out of control 

ASG is free, but you pay for the EC2 instances that are free, so thats why you might want to put a max to cap your costs. 
It also auto registers new EC2 to the load balancer, it's recreate an EC2 if for whatever reason the old one was terminated for being found unhealthy. 

So you'll set a min, a desired capacity, and a max capacity. 

Also the ELB can do a health check and then pass that info onto the ASG to auto scale unhealthy hosts to healthy hosts

ASG uses Launch Template
AMI, EC2 User Data, EBS Volumes, Sec Groups, SSH Key Pairs, IAM Roles for the EC2 instances, network + subnet info, load balancer info

Scaling Policies
CloudWatch can trigger an alarm which then signals to scale the ASG. (Average CPU of your EC2s -> add EC2 in ASG)

You can also schedule scaling - Xmas or friday night etc

Predictive scaling, looks at data and the generates a forcast to scale on. 

Good Meterics
CPU Utilization
RequestCountPerTarget
Average Network In/Out (network bound)

Scaling cool down
After you scale up or down it "Locks" so you can launch or terminate new EC2s. This allows the metrics to stablize for better measurements.

Default is 300 seconds. 

Best Practie, use ready to use AMIs to reduce the configuration time in order to serve requests faster and reduce the cooldown period
